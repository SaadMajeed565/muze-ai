# Security — Muze AI 0.5.0

## Threat model in one paragraph

The extension is the trust boundary. The gateway authenticates and routes, but it does not decide whether a browser action is allowed — the extension's policy engine, approval broker, and audit log do. A compromised or misbehaving MCP client must therefore still pass extension policy, approval, and scope checks. A compromised gateway connection alone must not be able to bypass those checks, which is why client-supplied confirmation flags are never approval (see README).

## Permissions

The extension manifest is intentionally broad — `<all_urls>`, debugger (CDP), tabs, tab groups, web navigation, scripting, storage, downloads, bookmarks, history, clipboard read/write, offscreen, side panel, identity, alarms. That breadth is what makes remote browser operation possible, and it is exactly why the in-code policy layer is load-bearing, not decorative. Do not weaken it without a corresponding review.

## What is enforced, and where

- **Policy (extension):** kill switch first, then restricted pages, blocked domains (exact or subdomain suffix, case-insensitive), client policy, manual denial, read-only gate, restricted-risk gate, permission-group gate, risk gate. A manual allow bypasses read-only and risk gates, but never the kill switch, restricted pages, blocked domains, client policy, or permission groups. Config patches cannot loosen a level's risk/approval gates without changing the level itself.
- **Approvals (extension):** single-use broker tokens, 120 second TTL, bound to tool + canonical input + client by a fast (non-cryptographic) fingerprint. The binding's strength rests on the random approval token, not on the fingerprint hash. Records are in-memory only and are lost on service-worker restart.
- **Audit (extension):** in-memory, capped (500 in the log class, 1000 in the service worker), newest-first. Details are key-redacted and call sites pass reason/code only — never token, password, or tool-input values. New in 0.3.0: dedicated `preflight-unavailable` decision (a failed gateway preflight is no longer recorded as an allow) and a dedicated `token.rotate` kind. (`token.reveal` was deleted with the token display removal in 0.5.0: no token value reaches the dashboard anymore.)
- **Rate limiting (extension):** per client + tool token bucket (120 capacity, 20/second refill in production wiring). Nested invokes take no second token in 0.3.0, matching the documented behaviour.
- **Rate limiting (gateway):** per-IP fixed windows per route via a Durable Object. Failure is fail-closed everywhere in 0.3.0: a limiter error or exception returns 503, never a silent pass. Credential-adjacent routes (login, signup, token, authorize, register, extension redeem, session, session rotate, logout, account, account delete, extension auth, revoke) are all rate-limited.
- **OAuth (gateway):** public clients only, S256 PKCE only, `response_type=code` required, dynamic registration open (throttled only by IP rate limit — registration alone grants nothing; authorisation still requires the signed-in website user). Access tokens 1 hour, refresh tokens 30 days with single-use rotation, authorization codes 5 minutes, extension codes 60 seconds, pair codes 10 minutes (pairing display only in 0.3.0; they do not authorise OAuth). Scopes `read:tools` and `call:tools` are enforced on tool calls (see README).
- **Tokens and passwords (gateway):** device and OAuth tokens are stored as SHA-256 hashes in the directory indexes, with one exception documented here: the account row stores the device token in clear so the website can return it to the extension on sign-in and rotation. Website passwords are PBKDF2-SHA256, 50,000 iterations, 16-byte salt. The 50,000 count is kept modest for Worker CPU budgets — it is not a substitute for a strong password policy (minimum length is 8 characters, enforced server-side).
- **Redaction:** three layers, not one — key-based redaction for logs/audit, pattern-based secret redaction for page text (JWTs, bearer/basic auth, key=value pairs, long hex/base64 blobs; it can miss secrets that do not match a pattern and can mask legitimate long blobs), and API-key/PEM scrubbing plus an untrusted-web-content wrapper applied to page reads. Other page-result paths are pattern-redacted but not wrapped. Screenshots and page data pass through the gateway unredacted, by design for a browser-control product — do not add a client that logs them.
- **Observer (extension):** when enabled, it runs in MAIN world on all URLs/frames, wraps alert/confirm/prompt/fetch/XMLHttpRequest, and records method, URL (capped), status, type, timing, and failure only. Request/response bodies are never recorded. Dialogs are answered with a sticky default (dismiss by default), which changes page behaviour by design.

## Known risks and deliberate choices

- **Device token at rest in the extension** is plaintext in `chrome.storage.local`. Rotation and masking reduce exposure; they do not encrypt it at rest. Treat any code running in extension context as able to read it.
- **Device token in the account row** is plaintext (see above). A storage dump of the directory alone does not reveal tokens from the hashed indexes, but the account row is an exception.
- **CDP trusted input** bypasses synthetic-event restrictions, including on React controlled inputs and some anti-bot checks. This is product behaviour. Attachment lifetime is now reference-counted and detached after each sequence, but the capability itself is privileged.
- **Directory Durable Object trusts its caller completely.** It has no authentication of its own; it is reachable only through Worker code. Never add a Worker route that forwards unchecked user input as a directory action name or payload.
- **Session Durable Object trusts Worker forwarding for WebSocket auth.** The first-message auth check inside SessionDO is the gate; a future Worker route that forwarded an upgrade to the wrong session would still be checked against the routed session id, but the trust boundary is implicit — keep it that way and review any new forwarding route.
- **No CAPTCHA or account lockout** on signup/login. Mitigation is IP rate limiting plus PBKDF2 only.
- **Open dynamic client registration** has no admin approval, listing, or deletion endpoint. Registration alone grants nothing.
- **Account deletion** purges directory rows, tokens, pair codes, and persisted MCP session records in SessionDO (0.3.0). Short-lived authorization requests/codes expire on their own (5–10 minutes) and are not separately purged.
- **In-memory security state** (approvals, audit, client registry, rate buckets) is lost on restart/eviction. Do not rely on audit history as a durable forensic log; export it if you need durability (no export exists in 0.5.0).
- **Tasks (0.4.0):** task state is durable in `chrome.storage.local` under `muze.tasks` (summaries only, never step inputs, page content, screenshots, passwords, or tokens), but approvals and audit remain in-memory. A task step still goes through the full executor policy/approval pipeline; task creation never pre-approves a step, and a client confirmation flag is never approval. Task ownership is by bridge client id (verified OAuth client id via the gateway, falling back to client name for direct bridge clients); OAuth scope for tasks is enforced at the gateway (`read:tools` may only get/list, `call:tools` is required for create/pause/resume/cancel) and is recorded in the extension snapshot as `gateway-enforced` because scope is not forwarded over the bridge. Direct executor calls to `tasks.*` fail with UNSUPPORTED; tasks must go through host dispatch to the runner. A bridge disconnect marks an in-flight step `unknown`, not failed, and it is re-observed before any retry — but a consequential step whose effect cannot be confirmed pauses for manual check rather than being blindly retried.
- **Task plan approval (0.5.0):** `tasks.approvePlan` never accepts a client-supplied approval flag. MCP callers use a broker approval token, verified as an approved token for `tasks.approvePlan` for the same client and then burned single-use (`ApprovalBroker.markUsed`); dashboard users use the dashboard decision. Approval expires at the task lifetime or 24 hours, whichever is shorter. Steps outside the approved bounds pause in `waiting_approval` with the reason; denial fails only that step. The executor's internal `planApproved` flag is set only by the TaskRunner after verifying an active in-bounds plan approval — it is not a tool-input field, is never forwarded from an MCP call, and policy checks still run per tool, so plan approval never overrides a policy denial.
- **Discovery and deprecation (0.5.0):** deprecated `navigate` tab/window actions and `data` devtools/clipboard domains still work in 2.x with warnings; they are never in the core set and are not removed in 0.5.0. Registry 3.0 removal is blocked on the gateway legacy adaptation mapping and on live-usage evidence, and must not be enabled silently.
- **Per-action risk (0.4.1):** unified calls resolve to a granular tool before scope, approval, rate limiting, and audit. An approval for `tabs.list` cannot authorise `tabs.close`; a `read:tools` client can list tabs through unified but cannot close them. Observe and act still fan out to many granular tools, so they keep unified-risk scope at the gateway and rely on granular gates in the extension. Delay waits (`wait` delay, `navigate` sync delay) have no granular tool and are flagged restricted in the action-risk table, but scope does not yet deny them — that is a deliberate non-breaking choice, recorded as a Phase 1 gap, not a silent policy change.

## Reporting

Do not paste tokens, passwords, or full tool inputs into a security report. Describe the version (0.5.0), the route or tool, the policy level, and the audit event kind/decision if you have it.
